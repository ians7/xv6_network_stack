High level description 
======================

In this project we are implementing a pthread-like library for threading on xv6.
We call our library ithread, and it allows for multiple threads to act on a
single address space at the same time within the same process, but doesn't worry
about concurency problems.

Already implemented:
- Threads forking to create new processes that are linked to a parent process.
- These threads are automatically directly linked to the parent process via a
  list in the process objects
- Threads exit like a normal process and can be joined to the main process
- Threads act on separate stacks from the main process and eachother, created
  with malloc(PAGESIZE)
- Threads now share the same memory space, can access each other's stacks, etc.
  
Thread Memory Propagation
==========================

We handle memory propagation with two simple functions. Whenever `growproc()` is
called by `sbrk()`, it checks if the process calling it was a thread. If it was
a thread, it calls our new function `uvmthreaded_alloc`, which takes in the
process instead of the pagetable of the process. This is so that the function
can access the highest level process, through which it can access the rest of
the threads. With this, it can loop over all of the threads to map the newly
allocated memory to each of their pagetables with `mappages()`.

As for deallocation with sbrk, we created a `uvmthreaded_dealloc()` function that
does something very similar to what our threaded alloc function does. It takes
the process that calls `sbrk()` and uses the access to the parent of the thread
to access all of the children. It then loops over the children and calls 
`uvmunmap()` on all the children.

Freeing the Stack 
================== 

Finally implemented during this final milestone. Due to our decision to allocate the
stack for our threads in userspace, it makes for a very simple solution to 
free our thread stacks.

We maintain an arraylist of stacks, a number of threads that have been created,
and a number of joined threads in order to track our stacks. When a thread is
created, a stack is allocated for it and a pointer to the stack is stored in our
arraylist of stacks. Whenever `ithread_free` is called by the user, it checks
that the number of joined threads is equal to the number of created threads. If
so, it calls the `free_stacks()` function, which frees all of the stacks that
have been created and resets the arraylist.

Test cases
===========

- (M2) Our thread creation test simply creates a thread and checks that the
       thread argument is passed to the thread by printing it.

- (M3) Our shared memory test has spawns 3 threads, each of which increments a 
       global integer `shared_counter` by one 50 times, i.e. shared_counter++;
       The test checks that `shared_counter` is equal to 200, and if it is, the
       code works. We know that the thread_join works because the program does
       not crash when we call thread_join on our threads.

- (M4) Our memory propagation test has two threads that it creates: One thread (T1)
       that calls sbrk, and one thread (T2) that tries to read from the memory 
       allocated by the other thread. After it allocates, T2 makes sure that it can
       see the value T1 places at that location. T1 waits until T2 is done
       checking, and then it deallocates the memory with sbrk. Once that it done,
       T2 tries to access the memory location. If this causes a kerneltrap, it
       passes the test. Otherwise, it fails.
